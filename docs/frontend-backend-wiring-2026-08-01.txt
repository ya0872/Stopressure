    ※ グローバルの python には uvicorn も fastapi も入っていない。
      必ず backend\.venv の python を使うこと。素の `python -m uvicorn ...` は

      仮想環境を有効化してから短く書いてもよい（実行ポリシーで弾かれることがある）。

--- ブラウザで開く ----------------------------------------------------------------

    ※ 127.0.0.1:5173 では繋がらない。Vite は ::1 でしか待ち受けないため、
      必ず localhost で開くこと。

--- 停止 --------------------------------------------------------------------------
    各ターミナルで Ctrl+C。効かない場合（孤児プロセスが残った場合）は次を実行。

    Get-CimInstance Win32_Process -Filter "Name = 'node.exe'" |
      Where-Object { $_.CommandLine -like '*vite*' } |
      ForEach-Object { Stop-Process -Id $_.ProcessId -Force }

    Get-CimInstance Win32_Process -Filter "Name = 'python.exe'" |
      Where-Object { $_.CommandLine -like '*uvicorn*' -or
                     $_.CommandLine -like '*multiprocessing-fork*' } |
      ForEach-Object { Stop-Process -Id $_.ProcessId -Force }

--- うまく動かないときの確認 -------------------------------------------------------
    # バックエンドが生きているか
    Invoke-RestMethod 'http://127.0.0.1:8000/api/v1/health'      # -> status: ok

    # 何がどのポートを握っているか
    Get-CimInstance Win32_Process -Filter "Name = 'python.exe'" |
      Select-Object ProcessId, CommandLine | Format-List
    Get-CimInstance Win32_Process -Filter "Name = 'node.exe'" |
      Select-Object ProcessId, CommandLine | Format-List

    ・コンソールに "blocked by CORS policy" が出る
        -> まずブラウザのアドレスバーのポート番号を見る。5173 以外（5174 など）に
           なっていたら、それが原因。バックエンドの CORS 許可リストは 5173 しか
           含まないため、Vite が別ポートで起動すると必ず弾かれる。
           Vite は 5173 が埋まっていると黙って 5174, 5175 …とずらす仕様だった。
           対策として vite.config.ts に strictPort: true を入れたので、現在は
           「Port 5173 is already in use」で起動時に落ちる。
           5173 を誰が握っているかは次で分かる。

           Get-NetTCPConnection -State Listen -LocalPort 5173,5174 |
             Select-Object LocalPort, OwningProcess
           Get-CimInstance Win32_Process -Filter "Name = 'node.exe'" |
             Where-Object { $_.CommandLine -like '*vite*' } |
             Select-Object ProcessId, CommandLine | Format-List

           不要なプロセスなら Stop-Process -Id <PID> -Force で落として起動し直す。

    ・画面に「バックエンドからデータを取得できませんでした」と出る
        -> ターミナル1の uvicorn が動いていない。上の health で確認する。
    ・404 が返る / 追加したはずのエンドポイントが無い
        -> --reload の孤児プロセスが古いコードを配っている。上の「停止」で全部落とす。
    ・接続先を変えたい
        -> frontend/.env の VITE_API_BASE を編集し、Vite を再起動する
           （HMR では反映されない）。既定は http://127.0.0.1:8000/api/v1。

■ 1. 着手前に存在していた問題
================================================================================

(1) ビルドが通らなかった
    frontend/src/main.tsx と frontend/.gitignore にマージのコンフリクトマーカー
    (<<<<<<< HEAD / ======= / >>>>>>>) が残っており、Vite が起動しなかった。

(2) 呼び先のエンドポイントが存在しなかった
    useWeatherStress.ts が `${API_BASE}/weather?lat=&lon=` を叩いていたが、
    バックエンドに /weather というルートは無い。実在するのは /atmosphere と /daily-plan。

(3) VITE_API_BASE が未定義だった
    frontend/.env が無いため URL が "undefined/weather" になり、fetch が必ず失敗。
    その失敗を catch がモックデータ（気圧998hPa・stressLevel:'HIGH'）で握りつぶしていた。
    → 画面上は正常に動いて見えるが、表示されていた値は全て偽物だった。
      体調に関わるアプリでこれは最も危険な壊れ方なので、フォールバックは廃止した。

(4) 型がバックエンドと噛み合っていなかった
    WeatherData に condition（天気テキスト）があるが、バックエンドは返さない。
    stressLevel は 'LOW'|'MEDIUM'|'HIGH'|'CRITICAL' の4段階だが、実際は 0〜100 の float。

(5) useEnergySavingTasks.ts が完全なモックだった
    setTimeout で固定3件を返すだけ。/daily-plan の suggestions を使っていなかった。

(6) node_modules が壊れていた（作業中に判明）
    node_modules/vite と node_modules/@types/node が空ディレクトリで、
    node_modules/.bin も存在しなかった。npm install が途中で中断された状態。
    → npm install で修復済み。

--------------------------------------------------------------------------------
3-2. 通信層（src/api/client.ts）
--------------------------------------------------------------------------------
URL の組み立てと fetch をこのファイルだけに閉じ込めた。

  const API_BASE = import.meta.env.VITE_API_BASE ?? 'http://127.0.0.1:8000/api/v1';

既定値を localhost ではなく 127.0.0.1 にしている理由:
  Windows のブラウザは localhost を先に ::1（IPv6）へ解決するが、uvicorn は
  --host 127.0.0.1 で待ち受けているため ::1 側は接続拒否になる（CLAUDE.md の注記）。

エラー処理:
  FastAPI は失敗時に {"detail": "..."} を返すので、本文を読んで ApiError.message に
  入れている。ステータスコードだけでは原因が分からないため。

公開している関数:
  fetchAtmosphere(coords, signal) -> AtmosphereResponse
  fetchDailyPlan(coords, signal)  -> DailyPlanResponse
  fetchHealth(signal)             -> {status}

--------------------------------------------------------------------------------
3-3. 取得の一元化（src/context/）
--------------------------------------------------------------------------------
/atmosphere と /daily-plan は同じ観測値から作られるため、Provider でまとめて
Promise.all で取得する。理由は2つ。

  ・widget ごとに fetch すると「気圧だけ新しくてレベルは古い」状態が起きうる
  ・hook ごとに Geolocation を呼ぶと許可ダイアログが複数回出る

自動更新は 5 分間隔（mockup/index.html と同じ）。気象は 1 時間粒度、Google 連携は
バックエンド側で 5 分キャッシュされるので、これより短くしても返る値は変わらない。
document.hidden のときは更新しない。

--------------------------------------------------------------------------------
3-4. 位置情報の扱い（src/hooks/useGeolocation.ts）
--------------------------------------------------------------------------------
取得できなかった場合、座標を null のままにしてクエリパラメータ自体を送らない。
バックエンドの既定地点（野々市 36.5297, 136.6094）が使われる。

  ※ 修正前は取得失敗時に東京（35.6812, 139.7671）を埋めていた。
     位置情報を拒否したユーザーに「別の土地の気圧」を本物の値として見せることになる
     ので、この挙動は廃止した。

■ 実機確認で見つかり、その場で直した欠陥 ■
  当初は「位置情報が決着するまで通信を始めない」実装にしていたが、
  許可ダイアログに応答しないと timeout(10秒)まで画面が「読み込み中」のままになった。
  → まず既定地点で取得を開始し、座標が確定したら取り直す方式へ変更。
    座標確定時には前の要求を AbortController で中断する。
    結果、初期表示は約 2 秒になった。

--------------------------------------------------------------------------------
3-5. 型の差し替え（src/types/weather.ts）
--------------------------------------------------------------------------------
バックエンドの Pydantic モデルの写しに置き換えた。フィールド名は snake_case のまま
保っている（camelCase へ変換すると、どちらの名前で書かれているか追えなくなるため）。

  StressDetail       {score, delta_6h, delta_24h, delta_next6h}
  ChartSeries        {times, pressure, now_index}
  AtmosphereResponse {latitude, longitude, observed_at, source, stale, pressure,
                      temperature, humidity, temp_delta_vs_yesterday,
                      discomfort_index, stress, chart}
  BreakdownItem      {factor, cost, cap, detail}
  SuggestionItem     {id, text, reason}          ← 完了フラグを持たない
  DailyPlanResponse  {date, energy_budget, level, level_name, headline,
                      suggest_title, level_driven_by_pressure, pressure_stress,
                      stale, google_context_used, breakdown, suggestions}

削除した型:
  StressLevel ('LOW'|'MEDIUM'|'HIGH'|'CRITICAL')
  WeatherData (condition を含む旧型)

--------------------------------------------------------------------------------
3-6. ストレスの4段階表示をやめた理由（設計上の判断）
--------------------------------------------------------------------------------
修正前は stressLevel を 4 段階のピル（安定 / やや注意 / 警戒 / 限界）で出していた。
これを維持するには「何点から警戒か」の閾値をフロントに持つ必要があるが、その定義は
backend/app/config/thresholds.yaml の stress_level_floor が唯一の持ち主であり、
CLAUDE.md が「スコアリング規則を JS に複製するな」と明示している。

代替として、
  ・ピルには気圧ストレス指数を数値でそのまま出す（例「気圧ストレス 2 / 100」）
  ・「今日は気圧のせい」と言い切ってよいかの判定は、サーバーが返す
    level_driven_by_pressure をそのまま使って注意文を出し分ける
とした。閾値はフロントに 1 つも持っていない。

  ※ dashboard.css の .pill.low/.medium/.high/.critical は未使用になったが、
    削除はしていない（他画面で使う可能性があるため。不要なら消してよい）。

--------------------------------------------------------------------------------

[夜の吐き出し] [設定] タブ … 未実装のまま（後述）

--------------------------------------------------------------------------------
3-8. バックエンド停止時の表示
--------------------------------------------------------------------------------
モックへのフォールバックを廃止した代わりに、状況を明示する通知を出す。

  ・未取得かつ失敗 : 「バックエンドからデータを取得できませんでした。（理由）」
                     ＋ uvicorn の起動コマンドを併記
  ・取得済みで更新失敗: 「表示中の値は HH:MM:SS 時点のものです」（古い値は保持）
  ・plan.stale が true: 「保存済みの観測値で算定しています」

免責事項（docs/design.md §1.4、実装必須）は全タブ共通のフッターに常時表示。
警告色・赤字は使っていない（取得失敗はユーザーの落ち度ではないため）。

--------------------------------------------------------------------------------
3-9. 製品上の禁止事項の遵守
--------------------------------------------------------------------------------
docs/design.md §1.2 の禁止事項に触れていないことを確認済み。

  ・提案にチェックボックス・完了操作を付けていない
    （SuggestionItem 型の段階で完了フラグを持たせていない）
  ・連続日数・前日比・繰り越しの表示なし
  ・Google 未連携時に連携を促す督促文言を出していない（事実の記載のみ）
  ・提案の選定・件数はサーバー（planner.pick_suggestions）に任せ、
    フロントで絞り込みや並べ替えをしていない

■ 6. 起動まわりの注意点
================================================================================
起動コマンドそのものはこのファイルの冒頭「■ 起動コマンド」を参照。
ここには理由の説明だけを残す。

  ・Vite は localhost（::1）でのみ待ち受ける。127.0.0.1:5173 では繋がらない。
    バックエンド側の CORS は localhost:5173 と 127.0.0.1:5173 の両方を許可済み
    （backend/app/main.py:27-31）なので、localhost で開けば実害はない。
  ・逆にバックエンドは --host 127.0.0.1 のままでよい。--host :: にすると IPv6 専用に
    なり 127.0.0.1 が死ぬ。--host 0.0.0.0 は設定APIをLANに晒すので使わない。
  ・frontend/.env を書き換えたら Vite の再起動が必要（HMR では反映されない）。
  ・.env を PowerShell で編集する場合、Set-Content -Encoding utf8 は BOM を付ける。
    BOM があるとキー名が "﻿VITE_API_BASE" となり Vite が読めない。
    実際に作業中これで一度ハマった。エディタで保存するか、次のようにする。
        [System.IO.File]::WriteAllText("$PWD\.env", "VITE_API_BASE=...", `
          (New-Object System.Text.UTF8Encoding $false))
