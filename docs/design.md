## 1. プロダクト定義

### 1.1 一行説明

現在地の天気・気圧データから身体的ストレスを推定し、**「今日は頑張らなくていい」という根拠を提示する**免罪符型ヘルスケアアプリ。

### 1.2 設計思想（最重要）

本アプリは**健康を改善しない**。改善するのは**罪悪感**である。

一般的なヘルスケアアプリは「目標未達＝ユーザーの怠慢」という構造を持ち、達成できないユーザーに負債感を蓄積させる。本アプリはこの構造を反転させ、不調の原因を**本人に制御不能な外部要因（気圧）に帰属**させることで、「何もしなかった日」を**正当な判断だった日**として再定義する。

### 1.3 禁止事項と、その例外（v0.2で精緻化）

新しいアイデア群（通知、称賛、ご褒美、振り返り）は、素朴に実装すると禁止事項と衝突する。**衝突しない条件**を以下に定める。

| 事項 | 禁止 | 許可される形 |
| --- | --- | --- |
| 通知 | **行動を促す事前通知**（「散歩しませんか」「まだ達成していません」） | **事後の肯定通知**のみ（「今日も無事に終わりました」）。行動要求を含まないこと |
| 称賛 | 達成量に比例する称賛（多くやった人ほど褒める） | **1つできたら満点**の称賛。ゼロでも「無事に過ごせた」を称賛対象とする |
| ご褒美 | ご褒美に**運動などの条件を課す**こと | 無条件のご褒美。運動系は**省エネレベル1〜2の日に限り**提示する |
| 振り返り | 未達成・空白日の可視化 | **できたことだけ**を表示。カレンダー形式は空白が目立つため**禁止**、リスト形式のみ |
| 記録 | 記録の義務化、連続記録の表示 | 任意入力。記録がない日は存在しないものとして扱う |

以下は**例外なく禁止**とする。

- 連続達成日数（ストリーク）の表示
- 未達成タスクの繰り越し・赤字表示
- 他ユーザーとの比較・ランキング
- 提案へのチェックボックス（完了/未完了の概念を持ち込まない）
- 「もっと頑張れる」方向の提案

### 1.4 免責事項（実装必須）

気象データと体調の関連は**体感の説明装置**として扱う。医学的診断・治療の代替ではない旨を、初回起動時とフッターに常時表示する。体調不良が続く場合は医療機関の受診を促す文言を含める。

### 3.3 LLMの使い分け（v0.3で変更）

| 用途 | 使用するLLM | 備考 |
| --- | --- | --- |
| **夜の吐き出しへの応答** | **Gemini** | v0.2では「ローカル固定」としていたが、利用者の判断により変更。入力内容はGoogleへ送信される |

**変更の経緯**: 版0.2ではプライバシーを理由に吐き出しをローカルLLM固定としていた。しかし実行環境に
Ollama / LM Studio が導入されておらず、導入コスト（数GBのダウンロード）に対して得られるものが
釣り合わないと判断された。将来ローカルLLMを導入した際に切り替えられるよう、生成部分は
`services/` 配下に分離しておく。

**実装要件**:

- **自由文を受け取るのは `/api/v1/reflection` のみ**とする。他の生成経路（`/api/v1/generate`）には
  自由文フィールド（`text` / `prompt` 等）を持たせない。これにより「ユーザーの言葉が外部へ出る経路」が
  1箇所に閉じ、監査対象が絞られる。**この構造は回帰テストで固定する**（`tests/test_generate_guard.py`）。
- 吐き出し画面には「入力内容が Gemini に送信される」ことを**常時表示**する。
- Gemini APIキーは Fernet で暗号化して SQLite に保存し、**APIから平文を返す経路を作らない**。
  画面にはマスク済み文字列のみを返す。
- 生成に失敗した場合も **200と定型文を返す**。ここでエラーを返すと「吐き出したのに無視された」
  体験になり、プロダクトの目的に反する。

## 4. ドメインロジック

### 4.1 気圧ストレス指数（中核アルゴリズム）

**設計判断**: 気圧の**絶対値ではなく変化率**を主軸にする。

理由は、体調不良と関連が指摘されるのは「低い気圧」そのものではなく「**気圧が急に下がる過程**」であるため。絶対値で判定すると、標高の高い地域では常時「低気圧」となり、台風一過の晴天日にも誤判定する。

```python
# 気圧ストレス指数の算出（0〜100、大きいほど身体負荷が高い）
def pressure_stress(hourly_pressure: list[float], now_index: int) -> float:
    """
    hourly_pressure: 1時間ごとの海面更正気圧(hPa)。過去24h〜予報12hを含む
    now_index: 現在時刻に対応するインデックス
    """
    p_now = hourly_pressure[now_index]

    # 短期変化: 直近6時間の低下幅（負の値ほど急降下）
    delta_6h = p_now - hourly_pressure[now_index - 6]
    # 長期変化: 直近24時間の低下幅
    delta_24h = p_now - hourly_pressure[now_index - 24]
    # 先行変化: これから6時間の予報低下幅（体調は先行して崩れるため加味）
    delta_next6h = hourly_pressure[now_index + 6] - p_now

    score = 0.0

    # 6時間で3hPa低下を基準点とし、1hPaあたり10点を加算（上限40点）
    if delta_6h < 0:
        score += min(abs(delta_6h) * 10, 40)

    # 24時間で10hPa低下を基準点とし、1hPaあたり3点を加算（上限30点）
    if delta_24h < 0:
        score += min(abs(delta_24h) * 3, 30)

    # 予報の下降は実測の半分の重みで先行評価（上限20点）
    if delta_next6h < 0:
        score += min(abs(delta_next6h) * 5, 20)

    # 絶対値は補助指標に留める。1000hPa未満で最大10点
    if p_now < 1000:
        score += min((1000 - p_now), 10)

    return min(score, 100.0)
```

**閾値の根拠**: 一般に気象病の目安として言及される「6時間で3hPa以上」「24時間で10hPa以上」の低下を基準点に置いた。本数値は体感との擦り合わせで**チューニング対象**とする（`config/thresholds.yaml` に外出し）。F-15 で個人ごとに自動調整する。

### 4.2 体力予算（Energy Budget）

気象以外の負荷因子を統合し、**その日に使える体力**を0〜100で表現する。

```python
# 本日の体力予算を算出（0〜100、小さいほど余裕がない）
def energy_budget(ctx: DailyContext) -> int:
    budget = 100.0

    # 気象ストレス（最大 -40）: 中核因子のため重みを最大にする
    budget -= pressure_stress(...) * 0.40

    # 気温の前日比（最大 -10）: 5℃以上の変化で身体は消耗する
    budget -= min(abs(ctx.temp_delta_vs_yesterday) * 2, 10)

    # 不快指数による湿度負荷（最大 -10）
    if ctx.discomfort_index >= 75:
        budget -= min((ctx.discomfort_index - 75), 10)

    # 睡眠不足（最大 -20）: 7時間を基準に不足1時間あたり5点
    if ctx.sleep_hours < 7:
        budget -= min((7 - ctx.sleep_hours) * 5, 20)

    # 予定による拘束（最大 -15）: 拘束1時間あたり2点
    budget -= min(ctx.busy_hours * 2, 15)

    # 要対応メール + ToDo（最大 -5）: 1件あたり1点
    budget -= min(ctx.actionable_mail_count + ctx.open_task_count, 5)

    return max(int(budget), 0)
```

**設計判断**: 各因子に**上限（キャップ）**を設け、単一因子が予算を食い尽くさないようにする。

### 4.2.1 レベル5の到達性 — **決定済み（2026-08-01）**

モックアップで検証した結果、**台風接近時（気圧ストレス93/100）でも省エネレベルは4止まり**になる。

気象因子の上限は `100 × 0.40 = 40点` であり、レベル5（予算19以下）に到達するには残り41点以上を**気圧以外の因子**で削る必要がある。実際にレベル5を再現するには「睡眠2時間・拘束5.5時間・メール15件・気温-6℃・湿度92%」を同時に成立させる必要があった。

**「気圧のせい」を掲げるプロダクトでありながら、最重度が気圧以外の理由でしか到達できない**という矛盾である。

**フェーズ1ではさらに深刻**であることが実装時に判明した。フェーズ1では睡眠（F-04/フェーズ2）・拘束（F-05/フェーズ3）・メール（F-06/フェーズ3）のデータが存在しないため、引ける点は `気象40 + 気温10 + 湿度10 = 最大60`。予算の下限が40となり、**レベル4と5は原理的に到達不可能**である。

| シナリオ | 気圧ストレス | 気象因子のみの予算 | 予算由来のLv |
| --- | --- | --- | --- |
| 台風接近 | 92.9 | 55 | 3 |
| 爆弾低気圧 | 92.5 | 48 | 3 |
| 梅雨の曇天 | 39.1 | 82 | 1 |

#### 決定: ストレス下限マッピング（案(c)の一般化）

```
level = max(体力予算から求めたレベル, 気圧ストレスから求めた下限レベル)
```

| 気圧ストレス | レベルの下限 |
| --- | --- |
| 90以上 | 5 |
| 75以上 | 4 |
| 55以上 | 3 |
| 35以上 | 2 |

**採否の理由**:

| 案 | 内容 | 評価 |
| --- | --- | --- |
| (a) | 気象の重みを 0.40 → 0.60 に上げる | **不採用**。フェーズ2以降で睡眠・拘束の影響が相対的に無意味になる。またLv5は依然として到達不可能 |
| (b) | レベル境界を変える（Lv5 を 0〜29 に） | **不採用**。予算の下限が40である以上、境界を動かしても届かない |
| (c) | 気圧ストレス90以上ならレベル5に固定 | **一般化して採用**。案(c)のままではフェーズ1でLv1とLv5しか出現せず、レベルが不連続に飛ぶ |

**「下限」であって「固定」ではない**点が重要である。フェーズ2以降で睡眠不足や拘束時間が加わり、予算由来のレベルがより深くなった場合はそちらが優先される。式の構造を変えないため、F-15（個人化）は従来どおり係数の調整だけで機能する。

**実装**: `backend/app/config/thresholds.yaml` の `stress_level_floor`、`backend/app/services/planner.py` の `resolve_level()`、および `mockup/index.html` の `toLevel()`。3箇所を同時に変更すること。

APIレスポンスの `level_driven_by_pressure` で、レベルが気圧側の下限で決まったかを判別できる。「今日は気圧のせいです」と言い切ってよい日かどうかの判定に使う。

### 4.3 省エネレベルと提案

| レベル | 体力予算 | 呼称 | 提案の性質 | 運動系ご褒美 |
| --- | --- | --- | --- | --- |
| 1 | 80〜100 | 平常運転 | やってもやらなくてもいい活動 | **可** |
| 2 | 60〜79 | 軽め | 座ったままできる活動 | **可** |
| 3 | 40〜59 | 省エネ | 生存維持のみ（白湯を飲む） | 不可 |
| 4 | 20〜39 | 深い省エネ | 休息そのもの（15分ボーッとする） | 不可 |
| 5 | 0〜19 | 完全休止 | **何もしないことが本日の目標** | 不可 |

**提案の選定ルール**:

- 提案は**そのレベル以下の負荷**を持つプールからのみ選ぶ（上振れ禁止）。
- 候補のうち**そのレベルで許される上限に近いものから**順に選ぶ。軽い順に選ぶと全レベルで「何もしない」が筆頭になり、レベルの差が消える（モックアップ実装時に判明した不具合）。
- 1日に提示するのは**最大3件**。多いこと自体が負荷になるため。
- レベル5では提案を**1件のみ**とする。
- 提案は**チェックボックスを持たない**。

### 4.4 献立提案（F-12）

目的は栄養管理ではなく、**「何を食べるか決める」という判断コストの除去**である。したがって以下を守る。

- 提示は**1案のみ**。選択肢を並べた時点で判断コストが発生する。
- 省エネレベルに応じて調理負荷を落とす。Lv4〜5では**調理しない選択肢**（買う・頼む・食べない）を提示する。
- 「食べなかった」ことを咎めない。

| レベル | 提案の例 |
| --- | --- |
| 1〜2 | 作る前提の献立（1品でよい） |
| 3 | 火を使わない、または温めるだけ |
| 4 | 買ってくる／頼む |
| 5 | 「食べられそうなものだけで十分です」 |

### 4.5 気圧耐性の個人化（F-15）

気象条件と本人の体感を突き合わせ、`thresholds.yaml` の係数を個人最適化する。

- 夜の吐き出し時に**体感を3段階**（つらかった／普通／平気）で任意記録する。入力は1タップ、スキップ可。
- 記録が**20日分**貯まった時点から、気圧ストレス指数と体感の相関を見て係数を調整する。
- 調整は**係数の増減のみ**とし、式の構造は変えない（説明可能性を保つため）。
- 「あなたは気圧の影響を受けやすい方です」といった**断定的な性格づけは行わない**。あくまで閾値の調整に留める。

**設計上の注意**: 記録を促す通知は出さない（§1.3）。記録がない日は学習対象から外すだけとする。

### 4.6 推定稼働率の表示（F-17）— 要検討事項

「現在の全国平均稼働率：12%」という表示について、**フェイクデータとしての実装は推奨しない**。

理由は2つある。第一に、**事実でない統計を事実として提示**することになり、アプリの他の数値（気圧・体力予算）の信頼性まで損なう。第二に、ハッカソンや公開の場で「このデータの出典は？」と問われた際に説明できない。

**代替案（推奨）**: 気圧ストレス指数から**機械的に算出した推定値**として提示する。これなら嘘ではなく、根拠も説明できる。

```python
# 全国の推定稼働率。気圧ストレスから機械的に導出するため「推定」と明示できる
def estimated_national_capacity(stress: float) -> int:
    """stress: 0〜100 の気圧ストレス指数"""
    return max(int(100 - stress * 0.9), 5)
```

表示は「**今日の気圧なら、みんなの稼働率もこのくらいです（推定）**」とし、**「平均」「実測」と誤解させる語を使わない**。ユーザーが得たい「みんな休んでる」という安心感は、この表現でも十分に得られる。

### 4.7 夜の全肯定レスポンス

音声またはテキストで吐き出された内容を受け、**Gemini**で肯定文を生成する（§3.3）。
実装は `backend/app/routers/reflection.py`。以下のシステムプロンプトを使用する。

```text
あなたはユーザーを全面的に肯定する聞き役です。以下を厳守してください。
- 助言、提案、励まし（「明日は頑張って」等）を一切含めない
- 原因をユーザーの努力不足に帰属させない
- 気象条件を根拠に「仕方がなかった」と外部帰属させる
- 2〜3文、100文字以内で応答する
- 「無事に過ごせただけで満点」という趣旨を必ず含める
```

生成テキストを VOICEVOX ENGINE（`localhost:50021`）で音声化する。**未起動時はテキスト表示にフォールバック**する。

### 4.8 利用フェーズ制限（F-16）

1日を4フェーズ（6時間ごと）に分け、**各フェーズ1時間のみ対話可能**とする。

- 起点は**その日に初めてアプリを開いた時刻**とする。固定時刻にすると生活リズムに合わない。
- 制限中は「次に話せるのは 18:00 です」と表示し、**省エネ度の閲覧は常時可能**にする。制限するのは対話機能のみ。
- 目的は依存の防止。ただし**「制限」という語をUIに出さない**（罰として受け取られるため）。「またあとで聞きます」といった表現にする。

## 6. データモデル（SQLite）

```sql
-- 睡眠記録。起床・就寝は手入力
CREATE TABLE sleep_log (
    date        TEXT PRIMARY KEY,
    bedtime     TEXT,
    wake_time   TEXT,
    created_at  TEXT NOT NULL
);

-- 気象スナップショット。API障害時のフォールバックとチューニング検証に使う。
-- latitude/longitude は版0.4で追加。地点で絞らないと、移動した際に別の都市の値を
-- 「今日の気圧」として提示してしまうため。
-- raw_json にはストレス指数を再計算できるだけの時系列（過去24h〜予報12h）を入れる。
CREATE TABLE atmosphere_snapshot (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    observed_at   TEXT NOT NULL,
    latitude      REAL NOT NULL,
    longitude     REAL NOT NULL,
    pressure      REAL NOT NULL,
    temperature   REAL,
    humidity      REAL,
    stress_score  REAL NOT NULL,
    source        TEXT NOT NULL,  -- 'jma' | 'open-meteo'
    raw_json      TEXT
);

-- 行動記録（F-10/F-14）。義務ではなく任意。無い日は行が存在しないだけ
CREATE TABLE activity_log (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    date       TEXT NOT NULL,
    category   TEXT NOT NULL,   -- 'meal' | 'move' | 'rest' | 'other'
    text       TEXT NOT NULL,
    created_at TEXT NOT NULL
);

-- 吐き出しログ。内容は機微情報のため外部送信しない
CREATE TABLE reflection (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    date         TEXT NOT NULL,
    user_text    TEXT NOT NULL,
    reply_text   TEXT NOT NULL,
    felt         INTEGER,        -- 体感 1:つらい 2:普通 3:平気（F-15の学習用、NULL可）
    created_at   TEXT NOT NULL
);

-- 個人化された閾値（F-15）
CREATE TABLE personal_threshold (
    key         TEXT PRIMARY KEY,
    value       REAL NOT NULL,
    samples     INTEGER NOT NULL,
    updated_at  TEXT NOT NULL
);

-- OAuthトークン。平文保存を避けFernetで暗号化する
CREATE TABLE oauth_token (
    provider      TEXT PRIMARY KEY,
    encrypted     BLOB NOT NULL,
    expires_at    TEXT,
    updated_at    TEXT NOT NULL
);
```

## 7. 外部連携

### 7.1 気象API — 気象庁とOpen-Meteoの併用（v0.2で訂正）

**訂正**: 版0.1では「気象庁APIでは気圧が取得できない」としていたが、これは**誤り**であった。実機検証の結果、以下が判明した。

| 項目 | 気象庁 アメダスJSON | Open-Meteo |
| --- | --- | --- |
| 実測気圧 | **取得可**（`normalPressure` = 海面気圧、`pressure` = 現地気圧） | 取得可 |
| 時間粒度 | **10分間隔**（Open-Meteoより細かい） | 1時間 |
| 過去分 | 約1週間 | 数か月 |
| **予報気圧** | **取得不可** | **取得可（最大16日）** |
| 費用 | 無料 | 無料（非商用） |
| APIキー | 不要 | 不要 |
| 安定性 | **非公式**。仕様変更の可能性あり | 公式API |
| 観測地点 | **気圧観測は気象官署のみ**。アメダス全地点では取れない | 任意の緯度経度 |

**検証結果（2026-08-01 実測）**: 金沢（観測所番号 `56227`）で `pressure: 1001.8` / `normalPressure: 1005.6` を10分間隔で取得できた。

```
https://www.jma.go.jp/bosai/amedas/data/latest_time.txt          # 最新観測時刻
https://www.jma.go.jp/bosai/amedas/data/point/56227/YYYYMMDD_HH.json  # 地点別（3時間分）
```

**採用方針**: 本アプリの中核アルゴリズムは**予報気圧を使う**（§4.1 の `delta_next6h`）。気象庁だけでは成立しないため、以下とする。

- **フェーズ1は Open-Meteo 単独**で実装する。実測と予報を1つのAPIで賄え、実装が最短になる。
- **フェーズ2以降で気象庁を実測側に併用**する。10分粒度で精度が上がり、「気象庁の公式データを使用」と言える利点がある。
- `atmosphere_snapshot.source` でどちらから得た値かを記録し、切り替え可能にしておく。

**注意点**: 野々市市には気圧観測点がないため、気象庁を使う場合は**金沢（56227）で代替**する。気圧は水平方向の変化が緩やかなため、数km程度の距離は実用上問題にならない。利用時は気象庁の利用規約（CC BY 4.0 相当）に従い、**出典を明記**すること。

### 7.2 Google Calendar / Gmail / Tasks

**重要な前提**: アプリ本体はローカル動作だが、**Google APIの利用にはGoogle Cloud Consoleでのプロジェクト作成とOAuthクライアント登録が必須**である。回避手段は存在しない。ローカル完結を厳守する場合は F-05 / F-06 / F-18 を落とし、拘束時間を手入力に切り替える（`config` のフラグで切替可能にする）。

| 項目 | 内容 |
| --- | --- |
| 認可方式 | OAuth 2.0 認可コードフロー（`http://localhost:8000/api/v1/auth/google/callback`） |
| Calendarスコープ | `calendar.readonly` |
| Gmailスコープ | `gmail.metadata`（**本文を取得しない**最小権限） |
| Tasksスコープ | `tasks.readonly` |
| トークン保存 | SQLite に Fernet 暗号化して保存。鍵は `.env` の `TOKEN_ENCRYPTION_KEY` |

**Gmailの用途**: 「要対応メール数」から**精神的負荷**を推定する目的に限定する。件名や本文の内容は利用しない。したがって `gmail.metadata` で足り、本文アクセス権を要求しない。審査リスクと心理的抵抗の両方を下げるための判断である。

#### 7.2.1 実装時の判断（版0.4）

| 項目 | 判断 | 理由 |
| --- | --- | --- |
| Gmailの取得方法 | `users.labels.get(id="IMPORTANT")` の `messagesUnread` のみ | メッセージ一覧すら取得しない。返るのは件数1つだけで、件名もIDも手に入らない |
| 終日予定 | 拘束時間に**数えない** | 「誕生日」等が24時間の拘束になると、体力予算が毎日ゼロになり気圧の影響が見えなくなる |
| 辞退した予定 | 数えない | 辞退した予定に拘束はされない |
| 重なる予定 | **マージ**して合算しない | ダブルブッキングは拘束が2倍になるわけではない |
| 期限の無いToDo | 数えない | 「いつかやる」は今日の負荷ではない |
| 期限切れのToDo | **数える** | §1.3 が禁じるのは繰り越しの**表示**であり、負荷としての勘定は禁じていない。数えることで予算が下がり、提案が軽くなる方向に働く |
| 取得失敗時 | 項目ごとに `None` のまま続行 | 3つのAPIは独立に失敗する。1つ落ちても残りは使える。`None` は「未計測」として内訳に現れない |
| 取得頻度 | 5分キャッシュ | `/daily-plan` は画面を開くたびに呼ばれる。予定が5分遅れて反映されても予算の精度に影響しない |

**未連携でもアプリは成立する**。連携していない場合、拘束・メール・ToDoは `None` のままとなり、フェーズ1と同じ挙動になる。`use_context` フラグを `false` にすると、連携を保ったまま予算への反映だけを止められる（§7.2 が求める切替に相当）。

#### 7.2.3 認証情報の取り違えを早く検出する

セットアップ時に実際に起きた3つの失敗と、その対策を記録する。**いずれもGoogle側のメッセージだけでは原因が特定できなかった**。

| 症状 | Googleの応答 | 実際の原因 | 対策 |
| --- | --- | --- | --- |
| 認可画面が出ない | `400 redirect_uri_mismatch` | リダイレクトURIが未登録 | 設定画面にURIとコピーボタンを常時表示 |
| 認可画面が出ない | `401 invalid_client` | client_id に空白と `@` が混入 | 保存時に形式を検査して422で弾く（`_CLIENT_ID_RE`） |
| ログインは通るが最後で失敗 | `invalid_client` (トークン交換時) | client_secret が別クライアントのもの | `POST /settings/google/test` で事前検証 |
| ログインは通るが最後で失敗 | `invalid_grant: Missing code verifier` | **実装の不具合**。PKCEの `code_verifier` を引き継いでいなかった | `state` と対で保持し、交換時に `flow.code_verifier` へ戻す |

**PKCE の落とし穴**: `google-auth-oauthlib` の `Flow` は `authorization_url()` を呼んだ時点で `code_verifier` を自動生成し、その SHA256 を `code_challenge` としてGoogleへ送る。コールバック側で `Flow` を作り直すと **verifier も作り直される**ため、認可時の値を持ち越さないと必ず失敗する。`_pending_states` は `state → code_verifier` の辞書であり、単なるCSRF対策ではない。**この対応関係を壊さないこと**（`tests/test_google_auth.py` の PKCE 4件で固定）。

**診断の教訓**: この不具合は画面のメッセージ（当初は `invalid_client` と表示されていた）からは特定できず、**サーバーログの例外を読んで初めて分かった**。連携の失敗を調べるときは、推測する前に `uvicorn` のログを見ること。`routers/auth_google.py` は失敗時に `exc_info=True` で全文を残す。

**シークレットの検証方法**: わざと無効な認可コードでトークン交換を試みる。Googleは、シークレットが違えば `invalid_client`、正しければ `invalid_grant`（コードが無効なだけ）を返す。この差でシークレットの正否だけを判定でき、認可画面を通す必要がない。

**Cloud Console の制約**: 既存のクライアントシークレットは**再表示できない**。紛失した場合は対象クライアントで新しいシークレットを追加し、作成直後にコピーする（複数のシークレットを併存させられるため、既存のものを消す必要はない）。

#### 7.2.2 判明した制約: Google連携だけではレベルが動かない

拘束時間の上限は15点、メール・ToDoの上限は5点で、**合計20点**。体力予算は80までしか下がらず、レベル1の下限がちょうど80であるため、**カレンダーが予定で埋まっていてもレベルは1のまま**になる。

これは §4.2.1 と同じ構造の問題である。Google連携は「レベルを動かす機能」ではなく、**気圧が悪い日の落ち込みを深める機能**として働く。

「予定が詰まっている日」を単独でレベルに反映させたい場合は、§4.2.1 と同様にストレス下限方式（拘束時間からもレベル下限を引く）を導入する必要がある。**本項は未決とする**（§11 #10）。

### 7.3 起床・就寝時刻の取得

**手入力を第一手段**とする。WebアプリからHealthKit / Google Fit のネイティブデータへ直接アクセスする手段がないため。

- カレンダーの当日最初の予定開始時刻を起床時刻の初期値として提案する。
- 入力は1タップで済ませる。入力自体が負荷になってはならない。

## 10. 実装フェーズ

**各フェーズ終了時点で単体でデモできる**ことを条件に分割する。

| フェーズ | 内容 | デモできること |
| --- | --- | --- |
| 0 | モックアップ（`mockup/index.html`）**完了** | 画面と体験の合意形成 |
| 1 | Open-Meteo → 気圧ストレス → 省エネレベル → 提案 **完了** | **アプリの核が成立**。外部認証不要 |
| 2 | 気圧グラフ、睡眠入力、予算内訳、朝／夜モード、気象庁併用 | 説得力のある画面が揃う |
| 3 | Google OAuth（Calendar/Gmail/Tasks）、行動ログ、トーン設定 | 「あなた専用」感が出る |
| 4 | 音声入力、ローカルLLM、VOICEVOX、献立、ご褒美、できたことログ | **情緒的なクライマックス** |
| 5 | 気圧耐性の個人化、フェーズ制限、推定稼働率 | 継続利用の価値を示せる |

**リスクと退避策**:

| リスク | 退避策 |
| --- | --- |
| Google OAuth の設定に時間を要する | フェーズ3を落としても他で完結する構成にしてある |
| Web Speech API が動かない | テキスト入力を最初から併設する |
| VOICEVOX / ローカルLLM が未起動 | テキスト表示・定型文にフォールバック |
| 気象庁APIの仕様変更 | 非公式APIのため、Open-Meteo を主系統に置き気象庁は補助に留める |
| 気圧の閾値が体感と合わない | `thresholds.yaml` で即時調整。F-15 で自動調整 |
