## 1. プロダクト定義

### 1.1 一行説明

現在地の気象データから身体的ストレスを推定し、**「今日は頑張らなくていい」という根拠を提示する**免罪符型ヘルスケアアプリ。

### 1.2 設計思想（最重要）

本アプリは**健康を改善しない**。改善するのは**罪悪感**である。

一般的なヘルスケアアプリは「目標未達＝ユーザーの怠慢」という構造を持ち、達成できないユーザーに負債感を蓄積させる。本アプリはこの構造を反転させ、不調の原因を**本人に制御不能な外部要因（気圧）に帰属**させることで、「何もしなかった日」を**正当な判断だった日**として再定義する。

この思想から、以下は**仕様上の禁止事項**とする。

| 禁止事項 | 理由 |
| --- | --- |
| 連続達成日数（ストリーク）の表示 | 途切れた瞬間に負債感が発生する |
| 未達成タスクの繰り越し・赤字表示 | 「やり残し」という概念自体を持ち込まない |
| 他ユーザーとの比較・ランキング | 相対評価は負荷である |
| 通知による行動の催促 | 催促は免罪符と矛盾する |
| 「もっと頑張れる」方向の提案 | 提案の負荷は上限を持ち、上振れさせない |

### 1.3 免責事項（実装必須）

気象データと体調の関連は**体感の説明装置**として扱う。医学的診断・治療の代替ではない旨を、初回起動時とフッターに常時表示する。体調不良が続く場合は医療機関の受診を促す文言を含める。

### 3.2 技術選定と根拠

| レイヤ | 採用 | 根拠 |
| --- | --- | --- |
| フロントエンド | React + TypeScript + Vite | 既存スキル。ビルドが速くハッカソン向き |
| 状態管理 | TanStack Query | サーバー状態が主体でクライアント状態がほぼ無いため、Redux等は過剰 |
| スタイル | Tailwind CSS | 低刺激なデザインを短時間で詰めるため |
| バックエンド | FastAPI | 型定義からOpenAPIが自動生成され、フロントとの契約が固まる |
| DB | SQLite | 単一ユーザーのローカル運用に十分。サーバープロセス不要 |
| LLM | Ollama + Gemma | 既存環境。吐き出し内容を外部送信しないため**プライバシー上も必須** |
| 音声合成 | VOICEVOX ENGINE | ローカル完結。声質を「癒やし」方向に選定可能 |
| 音声認識 | Web Speech API | 追加実装ゼロ。Chrome前提のため**テキスト入力を必ず併設** |

**気象APIの選定**: **Open-Meteo** を採用する。

- 気象庁APIは**気圧の予報値を配信していない**ため、本アプリの中核指標が作れず不採用。
- OpenWeatherMapは無料枠でAPIキー管理が必要。Open-Meteoは**APIキー不要・非商用無料・時間粒度の気圧/気温/湿度を過去分と予報分の両方**で返すため、要件に完全に一致する。

## 4. ドメインロジック

### 4.1 気圧ストレス指数（中核アルゴリズム）

**設計判断**: 気圧の**絶対値ではなく変化率**を主軸にする。

理由は、体調不良と関連が指摘されるのは「低い気圧」そのものではなく「**気圧が急に下がる過程**」であるため。絶対値で判定すると、標高の高い地域では常時「低気圧」となり、台風一過の晴天日にも誤判定する。

```python
# 気圧ストレス指数の算出（0〜100、大きいほど身体負荷が高い）
def pressure_stress(hourly_pressure: list[float], now_index: int) -> float:
    """
    hourly_pressure: 1時間ごとの海面更正気圧(hPa)。過去24h〜予報12hを含む
    now_index: 現在時刻に対応するインデックス
    """
    p_now = hourly_pressure[now_index]

    # 短期変化: 直近6時間の低下幅（負の値ほど急降下）
    delta_6h = p_now - hourly_pressure[now_index - 6]
    # 長期変化: 直近24時間の低下幅
    delta_24h = p_now - hourly_pressure[now_index - 24]
    # 先行変化: これから6時間の予報低下幅（体調は先行して崩れるため加味）
    delta_next6h = hourly_pressure[now_index + 6] - p_now

    score = 0.0

    # 6時間で3hPa低下を基準点とし、1hPaあたり10点を加算（上限40点）
    if delta_6h < 0:
        score += min(abs(delta_6h) * 10, 40)

    # 24時間で10hPa低下を基準点とし、1hPaあたり3点を加算（上限30点）
    if delta_24h < 0:
        score += min(abs(delta_24h) * 3, 30)

    # 予報の下降は実測の半分の重みで先行評価（上限20点）
    if delta_next6h < 0:
        score += min(abs(delta_next6h) * 5, 20)

    # 絶対値は補助指標に留める。1000hPa未満で最大10点
    if p_now < 1000:
        score += min((1000 - p_now), 10)

    return min(score, 100.0)
```

**閾値の根拠**: 一般に気象病の目安として言及される「6時間で3hPa以上」「24時間で10hPa以上」の低下を基準点に置き、そこで中程度のスコアに到達するよう係数を設定した。本数値は体感との擦り合わせで**チューニング対象**とする（`config/thresholds.yaml` に外出しし、コード変更なしで調整可能にする）。

### 4.2 体力予算（Energy Budget）

気象以外の負荷因子を統合し、**その日に使える体力**を0〜100で表現する。

```python
# 本日の体力予算を算出（0〜100、小さいほど余裕がない）
def energy_budget(ctx: DailyContext) -> int:
    budget = 100.0

    # 気象ストレス（最大 -40）: 中核因子のため重みを最大にする
    budget -= pressure_stress(...) * 0.40

    # 気温の前日比（最大 -10）: 5℃以上の変化で身体は消耗する
    budget -= min(abs(ctx.temp_delta_vs_yesterday) * 2, 10)

    # 不快指数による湿度負荷（最大 -10）
    if ctx.discomfort_index >= 75:
        budget -= min((ctx.discomfort_index - 75), 10)

    # 睡眠不足（最大 -20）: 7時間を基準に不足1時間あたり5点
    if ctx.sleep_hours < 7:
        budget -= min((7 - ctx.sleep_hours) * 5, 20)

    # 予定による拘束（最大 -15）: 拘束1時間あたり2点
    budget -= min(ctx.busy_hours * 2, 15)

    # 要対応メール（最大 -5）: 1件あたり1点
    budget -= min(ctx.actionable_mail_count * 1, 5)

    return max(int(budget), 0)
```

**設計判断**: 各因子に**上限（キャップ）**を設けている。これは単一因子が突出して予算を食い尽くし、「気圧は穏やかなのに省エネ度が最大」といった説明のつかない結果を防ぐため。ユーザーへの提示時は「何が予算を削ったか」の内訳を必ず開示する。

### 4.3 省エネレベルと提案

体力予算を5段階の**省エネレベル**に写像する。レベルが高いほど「何もしない」に近づく。

| レベル | 体力予算 | 呼称 | 提案の性質 |
| --- | --- | --- | --- |
| 1 | 80〜100 | 平常運転 | やってもやらなくてもいい活動（散歩など） |
| 2 | 60〜79 | 軽め | 座ってできる活動（読書、音楽） |
| 3 | 40〜59 | 省エネ | 生存維持のみ（白湯を飲む、水分補給） |
| 4 | 20〜39 | 深い省エネ | 休息そのもの（15分ボーッとする、横になる） |
| 5 | 0〜19 | 完全休止 | **何もしないことが本日の目標** |

**提案の選定ルール**:

- 提案は**そのレベル以下の負荷**を持つプールからのみ選ぶ（上振れ禁止）。
- 1日に提示するのは**最大3件**。多いこと自体が負荷になるため。
- レベル5では提案を**1件のみ**（「今日は何もしないでください」）とする。
- 提案は**チェックボックスを持たない**。完了/未完了の概念を導入しない。

提案データは `data/suggestions.yaml` に静的定義する（LLM生成にしないのは、負荷の上限保証をコードで担保できないため）。

```yaml
# 提案プールの定義例。max_level 以上のレベルでは提示されない
- id: sayu
  text: 白湯を飲む
  load: 3          # 負荷レベル（1が最も重い、5が最も軽い）
  reason: 内臓を温めると自律神経が落ち着きやすいとされます
- id: stare
  text: 15分ボーッとする
  load: 4
  reason: 何も考えない時間は脳の回復に使われます
- id: nothing
  text: 何もしない
  load: 5
  reason: 今日はそれが最適解です
```

### 4.4 夜の全肯定レスポンス

音声またはテキストで吐き出された内容を受け、**ローカルLLM（Ollama + Gemma）**で肯定文を生成する。

**設計判断**: 外部API（Claude/GPT等）を使わない。吐き出しの内容は極めて私的であり、**ローカル完結が本機能の前提条件**である。

システムプロンプトの制約:

```text
あなたはユーザーを全面的に肯定する聞き役です。以下を厳守してください。
- 助言、提案、励まし（「明日は頑張って」等）を一切含めない
- 原因をユーザーの努力不足に帰属させない
- 気象条件を根拠に「仕方がなかった」と外部帰属させる
- 2〜3文、100文字以内で応答する
- 「無事に過ごせただけで満点」という趣旨を必ず含める
```

生成テキストを VOICEVOX ENGINE（`localhost:50021`）に渡して音声化し、フロントで再生する。**VOICEVOXが未起動の場合はテキスト表示にフォールバック**する。

## 6. データモデル（SQLite）

```sql
-- 睡眠記録。起床・就寝は手入力（WebアプリからはHealthKit等を参照できないため）
CREATE TABLE sleep_log (
    date        TEXT PRIMARY KEY,  -- YYYY-MM-DD
    bedtime     TEXT,              -- HH:MM（前日の就寝時刻）
    wake_time   TEXT,              -- HH:MM
    created_at  TEXT NOT NULL
);

-- 気象スナップショット。API障害時のフォールバックとチューニング検証に使う
CREATE TABLE atmosphere_snapshot (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    observed_at   TEXT NOT NULL,
    pressure      REAL NOT NULL,
    temperature   REAL,
    humidity      REAL,
    stress_score  REAL NOT NULL,
    raw_json      TEXT
);

-- 吐き出しログ。内容は機微情報のため外部送信しない
CREATE TABLE reflection (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    date         TEXT NOT NULL,
    user_text    TEXT NOT NULL,
    reply_text   TEXT NOT NULL,
    created_at   TEXT NOT NULL
);

-- OAuthトークン。平文保存を避けFernetで暗号化する
CREATE TABLE oauth_token (
    provider      TEXT PRIMARY KEY,  -- 'google'
    encrypted     BLOB NOT NULL,
    expires_at    TEXT,
    updated_at    TEXT NOT NULL
);
```

## 7. 外部連携

### 7.1 Open-Meteo

- エンドポイント: `https://api.open-meteo.com/v1/forecast`
- パラメータ: `hourly=pressure_msl,temperature_2m,relative_humidity_2m`, `past_days=2`, `forecast_days=2`, `timezone=Asia/Tokyo`
- 認証: 不要
- **キャッシュ**: 同一地点・同一時刻のリクエストは1時間キャッシュする（気圧は時間粒度のため、それ以上の頻度で取得する意味がない）。

### 7.2 Google Calendar / Gmail

**重要な前提**: アプリ本体はローカル動作だが、**Google APIの利用にはGoogle Cloud Consoleでのプロジェクト作成とOAuthクライアント登録が必須**である。これはホスティングのクラウド利用とは別問題であり、回避手段は存在しない。ローカル完結を厳守したい場合は F-05 / F-06 を落とし、拘束時間を手入力に切り替える設計に退避できる（`config` のフラグで切替可能にする）。

| 項目 | 内容 |
| --- | --- |
| 認可方式 | OAuth 2.0 認可コードフロー（`http://localhost:8000/api/v1/auth/google/callback`） |
| Calendarスコープ | `calendar.readonly` |
| Gmailスコープ | `gmail.metadata`（**本文を取得しない**最小権限） |
| トークン保存 | SQLite に Fernet 暗号化して保存。鍵は `.env` の `TOKEN_ENCRYPTION_KEY` |

**Gmailの用途を確定する**: 「要対応メール数」から**精神的負荷**を推定する目的に限定する。件名や本文の内容は利用しない。したがって `gmail.metadata` スコープで足り、本文アクセス権を要求しない。これは審査リスクと心理的抵抗の両方を下げるための判断である。

- 判定条件: 受信トレイの未読、かつ過去72時間以内、かつ自分宛（`to` に自分を含む）
- 上限: 20件で頭打ち（それ以上数えても負荷推定の精度は上がらない）

### 7.3 起床・就寝時刻の取得

**手入力を第一手段**とする。理由は、WebアプリからHealthKit / Google Fit のネイティブデータへ直接アクセスする手段がないため。

- 補助として、カレンダーの当日最初の予定開始時刻を起床時刻の初期値として提案する。
- 入力を1タップで済ませる（「7時に起きた」等のプリセットボタン）。入力自体が負荷になってはならない。

### 8.1 画面構成

| ホーム | 省エネレベル、ヘッドライン、提案（最大3件）、予算内訳 |

### 8.2 デザイン方針

- **低刺激**: 彩度を抑えた配色。白背景は使わず、офф-white〜ダークを基調にする。
- **アニメーションは緩慢に**: トランジションは 400ms 以上のイージングとし、跳ねる挙動（バウンス）を使わない。
- **通知しない**: プッシュ通知・バッジは実装しない。ユーザーが開いたときだけ存在する。
- **アクセシビリティ**: 気圧グラフの情報は色だけに依存させず、数値とテキストで併記する。

## 10. 実装フェーズ

ハッカソン想定のため、**各フェーズ終了時点で単体でデモできる**ことを条件に分割する。

| フェーズ | 内容 | デモできること |
| --- | --- | --- |
| 1 | Open-Meteo取得 → 気圧ストレス → 省エネレベル → 提案表示 | **アプリの核が成立**。外部認証不要で確実に動く |
| 2 | 気圧グラフ、睡眠時刻の手入力、予算内訳の開示 | 説得力のある画面が揃う |
| 3 | Google OAuth、Calendar拘束時間、Gmail負荷 | 「あなた専用」感が出る |
| 4 | 音声入力、Ollama肯定文生成、VOICEVOX読み上げ | **情緒的なクライマックス**を作れる |

**リスクと退避策**:

| リスク | 退避策 |
| --- | --- |
| Google OAuth の設定に時間を要する | フェーズ3を落としても1・2・4で完結する構成にしてある |
| Web Speech API が動かない | テキスト入力を最初から併設する |
| VOICEVOX / Ollama が未起動 | いずれもテキスト表示・定型文にフォールバックする |
| 気圧の閾値が体感と合わない | `thresholds.yaml` で即時調整できる |
