AIチャット入力欄（Healing.tsx）とバックエンドの接続状況 調査結果
低気圧のすゝめ / Atmosphere Studio
調査日: 2026-08-02   対象ブランチ: beta

■ 結論
================================================================================
**接続されている。** 実際に Gemini の生成結果が返ってくることを確認した。

ただし「繋がっていないのでは」と疑うのが自然な作りになっている。
Healing.tsx は**通信の失敗を成功と見分けがつかない形で握り潰す**ため、
バックエンドが落ちていても、APIキーが無くても、画面には同じような肯定文が出る。
そのため画面を見ているだけでは、接続の成否を判断できない。

疑いの出どころはここだと考えられる。以下、確認した内容と、直すべき点を挙げる。


■ 接続されている根拠（6点）
================================================================================

 1. 環境変数が定義されている
      frontend/.env に VITE_API_BASE=http://127.0.0.1:8000/api/v1 がある。

 2. Vite がその .env を読み込み済み
      .env 最終更新 : 2026-08-02 09:36:05
      Vite 起動時刻 : 2026-08-02 09:36:18   ← .env より後に起動している
      Vite は起動時にしか .env を読まないので、この順序なら反映されている。

 3. 画面に配線されている
      Dashboard.tsx:304 の「夜の吐き出し」ビューで <Healing /> が描画されている。
      孤立したコンポーネントではない。

 4. CORS が通っている
      OPTIONS /api/v1/reflection に Origin: http://localhost:5173 を付けて確認。
        → access-control-allow-origin: http://localhost:5173

 5. 実際に送って応答が返る
      Healing.tsx が組み立てるのと同じURL・同じヘッダで実送信した。
        POST http://127.0.0.1:8000/api/v1/reflection
        {"text":"接続確認のテスト送信です"}
      →  {"reply":"接続確認のテスト送信、受け取りました。\n今日も無事に過ごせた
          だけで満点です。","model":"gemini-2.5-flash","fallback":false}
      fallback:false なので、定型文ではなく Gemini が実際に生成している。

 6. Gemini 側の設定も生きている
      GET /api/v1/settings/gemini
      → {"configured":true,"source":"env","model":"gemini-2.5-flash",
         "sdk_installed":true}

 参考: dist/assets/main-*.js（過去のビルド成果物）にも 127.0.0.1:8000/api/v1 が
 埋め込まれており、"undefined/reflection" は含まれていない。ビルド時にも .env は
 正しく読まれていた。


■ なぜ「繋がっていない」ように見えるのか
================================================================================
Healing.tsx:40-51 が原因。

    let reply: string;
    if (res.ok) {
        const json = await res.json();
        reply = json.reply;
    } else {
        reply = FALLBACK_REPLY;        // ← 全部ここに落ちる
    }
    ...
    } catch {
        setMessages(... FALLBACK_REPLY);   // ← ネットワークエラーもここ
    }

この書き方だと、次のすべてが画面上で同じに見える。

    バックエンドが起動していない        → FALLBACK_REPLY
    Gemini APIキーが未設定（409）       → FALLBACK_REPLY
    URLが間違っている（404）            → FALLBACK_REPLY
    Gemini がエラー（バックエンドは200 + fallback:true）→ その定型文
    正常に生成された                    → Gemini の応答

「無事に一日を終えられただけで満点です。…」という**それらしい文が必ず返るので、
失敗しても失敗に見えない**。ユーザーから見ると「AIが答えていない気がする」という
形でしか異常に気づけない。これは接続の問題ではなく、エラー表示の問題である。


■ 見つかった問題（優先度順）
================================================================================

--- 問題1: 失敗が握り潰されている（Healing.tsx:44, 50）--------------------------
上に書いたとおり。**接続確認ができないのはこれが理由**。

ただし「必ず何かを返す」という方針自体は正しい。バックエンド側の
routers/reflection.py にも同じ思想があり、「ここで500を返すと『吐き出したのに
無視された』体験になる」という理由でエラーを握っている。

なので消すべきではなく、**肯定文は出したうえで、状態を小さく併記する**のがよい。
    例:「いまバックエンドに接続できていません」を吹き出しの下に淡色で出す
禁止事項（§1.2 の督促の禁止）に触れないよう、責める文言にはしないこと。

--- 問題2: API_BASE にフォールバックが無い（Healing.tsx:10）--------------------
    Healing.tsx:10   const API_BASE = import.meta.env.VITE_API_BASE;
    client.ts:16     const API_BASE = import.meta.env.VITE_API_BASE ?? 'http://127.0.0.1:8000/api/v1';
    console/api.ts:28 も ?? でフォールバックを持っている

Healing.tsx だけ既定値が無い。**この環境では .env があるので動いているが、
.env が無い環境（clone 直後、別のPC、CI）では API_BASE が undefined になり、
fetch("undefined/reflection") が相対URLとして解釈されて
http://localhost:5173/undefined/reflection を叩き、404 → 問題1により
FALLBACK_REPLY が出る。**つまり黙って壊れ、画面上は正常に見える。

.env は .gitignore で除外されている（追跡されているのは .env.example だけ）ので、
リポジトリを clone した人は必ずこの状態になる。

--- 問題3: fallback フラグを使っていない（Healing.tsx:42-43）-------------------
バックエンドは {"reply":..., "model":..., "fallback":true/false} を返し、
fallback:true が「生成に失敗して定型文を返した」を意味する。Healing.tsx は
reply しか読んでいないので、この情報が捨てられている。

2026-08-02 に追加した利用回数の上限（F-16）でも、上限到達時は
fallback:true + model:null で定型文が返る。フラグを見ていないため、
**上限に達したことが画面にまったく現れない**。

--- 問題4: client.ts を経由していない生fetch（Healing.tsx:34）------------------
client.ts の冒頭にこう書いてある。

    「ここより上ではURLの組み立てや fetch を書かない。エンドポイントが増減した
      ときに探す場所を1箇所に保つため。」

Healing.tsx はこれを守っておらず、独自に API_BASE と fetch を持っている。
問題2（フォールバックの欠落）はこの分岐が原因で生まれている。
client.ts に postReflection() を足して寄せるのが筋。

--- 問題5: level と felt を送っていない（Healing.tsx:37）-----------------------
    body: JSON.stringify({ text: userText })

バックエンドの ReflectionRequest は level（省エネレベル）と felt（体感 1〜3）も
受け取れる。felt は F-15（気圧耐性の個人化）の学習データになる想定だが、
送っていないので reflection テーブルには常に NULL が入っている。

level は useAtmosphere() から取れる（Dashboard.tsx が既に持っている）。
felt はUIが無いので、入力手段を作るかどうかの判断が要る。


■ 接続とは別に見つかったこと
================================================================================
frontend/.env に GOOGLE_CLIENT_SECRET が置かれている。

    - フロントエンドのコードでは使われていない（main.tsx が使うのは
      VITE_GOOGLE_CLIENT_ID だけ）。VITE_ が付いていないので Vite はバンドルに
      埋め込まず、実質どこからも読まれていない。
    - この値はバックエンドが持つべきもので、frontend/.env に置く理由がない。
    - .gitignore で .env と .env.* が除外されており、git ls-files で確認した
      ところ追跡されているのは .env.example だけなので、**リポジトリへの漏洩は
      起きていない**。dist/ にも埋め込まれていない（確認済み）。
    - ただし置き場所としては誤り。backend/.env へ移すか、フロントから消すのが
      望ましい。実値はこのファイルには書かない。


■ 直すなら（提案）
================================================================================
 1. Healing.tsx を client.ts 経由にする
      client.ts に postReflection(text, level?, felt?) を足し、Healing.tsx から
      生fetchを消す。これで問題2と問題4が同時に消える。

 2. 失敗の種類を画面に出す（肯定文は出したまま）
      res.ok=false / catch / fallback:true をそれぞれ区別し、吹き出しの下に
      淡色の一行を添える。責める文言にはしない。
        接続不可     「いま接続できていません。あとでもう一度お試しください」
        キー未設定   「設定画面から Gemini APIキーを登録してください」
        上限到達     「今日はもう十分に言葉にできています」（§4.8 の言い回し）

 3. level を送る
      Dashboard.tsx が既に plan.level を持っているので、props か context で渡す。

 4. frontend/.env から GOOGLE_CLIENT_SECRET を消す

 なお 1〜3 は「フロントエンドの修正」であり、今回の調査依頼の範囲外なので
 実装はしていない。指示があれば着手する。
